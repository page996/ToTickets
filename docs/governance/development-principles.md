# 开发原则与模块治理

**版本**：`development-principles.v1`  
**生效日期**：2026-09-02  
**适用范围**：本仓库的源码、测试、文档、工具链、构建和部署准备

## 1. 作用域与优先级

本文件把项目维护者确认的开发原则落成仓库内可审计的规则。它与根目录
`AGENTS.md`、`docs/governance/approval-protocol.md` 一起约束后续代理和贡献者；不尝试
修改 Codex 的隐藏 system prompt，也不要求记录隐藏思维链。发生冲突时，平台安全规则和
用户明确的最新决策优先，随后是 `AGENTS.md` 与本治理文件。

结论和记录必须标注为：

- **已由代码/测试确认**：有可复现命令、测试或构建证据；
- **工程假设**：作为设计起点但尚未实测；
- **待用户/平台确认**：需要人工验收、外部供应商或用户选择。

## 2. 模块化与模块开发书

### 2.1 分解规则

每项开发先定义一个或多个独立模块，再定义连接关系。模块必须有清晰的职责、非职责、
输入、输出、错误边界和可替换端口；模块完成前不得把临时内部类、共享表结构或未版本化
状态直接暴露给其他模块。该规则递归应用于模块内部的 service、repository、adapter、
transport、UI feature 和测试 harness。

高层架构图、模块连接矩阵和接口总表可以作为索引，但不能替代逐模块开发书。模块书的
推荐路径为 `docs/modules/<module-id>.md`，模块 ID 必须稳定且能映射到源码目录或明确的
计划边界。

### 2.2 模块开发书最低字段

每个模块及其子模块至少记录：

1. `module_id`、版本、状态（planned/active/verified/deprecated）和负责人边界；
2. 职责、非职责、状态机、不变量，以及所有模块内变量/持久化字段的所有权；
3. 对外函数/端口的签名、前置条件、后置条件、错误码、超时和幂等语义；
4. REST、WebSocket、CloudEvents、进程或设备通信的版本化 schema、方向和副作用；
5. 共享资源、锁/队列、配置键和数据保留策略，以及谁可以读写；
6. test-only port、fixture/harness、契约测试、负向测试、审计断言和禁止的测试路径；
7. 已完成的 checkpoint、证据位置、连接门槛和回滚方法；
8. 与其他模块的连接表，以及连接建立前必须通过的检查。

子模块必须有自己的条目；仅在父模块中用一段文字描述，不视为递归开发书。

## 3. 依赖与运行环境

开发和测试必须从仓库内版本化、可复现的项目隔离环境启动，并在其中调用锁定的 Node、
pnpm、Rust 和其他工具链。系统级 Node、Rust、Python、全局包或未声明的 Android 工具不
得成为项目假设。现有 `.tools` wrapper、版本文件、锁文件和 Rust toolchain 是当前隔离
实现的一部分；每个入口还必须记录启动校验、缓存位置和新机器复现步骤，不能回退到系统
运行时。

依赖变更必须同时更新 manifest、锁文件、许可证/维护状态、SBOM、权限面、来源和替代方案。
本机文档、输入文件、用户目录、绝对路径、其他项目路径、凭据和 GitHub 开源项目实现不得
硬编码到源码、测试夹具、配置默认值或打包脚本。文档可以引用外部来源，但必须标记为
研究来源，不能被运行时复用。开源项目只能借鉴接口/风险并按本项目边界本地化重写；成品
运行时依赖必须随项目封装并可校验。

## 4. 系统 helper 白名单

项目保留受控系统 helper 的接入空间，用于宿主机探测、已批准的构建/设备生命周期或其他
明确的辅助职责；这不等于允许任意系统命令，也不改变真实大麦只能人工操作的边界。

helper 接入必须先登记 `system-helper-manifest.v1`，至少包含：

1. 稳定的 `helper_id`、精确版本、来源、文件哈希、许可证/维护状态和责任人；
2. 目的、允许能力和明确禁止能力（尤其是输入、自动化、凭据、交易和外部网络）；
3. 用户批准的可执行路径或项目内封装位置、允许参数/环境变量、工作目录和子进程规则；
4. 输入/输出数据类型、敏感数据处理、网络/文件访问范围、CPU/内存/磁盘上限；
5. 启动、健康、停止、超时、崩溃恢复、审计事件、撤销和回滚方式；
6. 使用的版本化模块端口、契约测试、负向测试和关联 checkpoint。

运行时只接受白名单条目与用户显式选择的路径，禁止 PATH、注册表、用户目录或模糊名称
猜测；哈希、版本、能力或路径任一不匹配都必须 fail closed。helper 不得直接读写其他
模块的数据库表、共享可变状态或未版本化内部类，也不得绕过配置校验、人工确认和适配器
能力门禁。隐藏 system prompt 不属于 helper 接入面。

## 5. 专用测试入口

每个可测试模块必须提供版本化且明确标记为 test-only 的 port、fixture 或 harness。测试
通过该入口注入时钟、容量、适配器、故障和合成数据；生产 controller、真实 provider 和
用户数据路径不得作为测试捷径。每个入口至少有：

- 正常路径单元测试和跨模块契约测试；
- 未知字段、权限、容量、并发、重放、失败恢复等负向测试；
- 对敏感数据不落盘、拒绝事件和副作用边界的审计断言；
- 可重复的命令、配置来源和清理步骤。

真实大麦或其他真实交易平台只允许用户人工验收，不能通过测试入口自动登录、识别、点击、
选票、下单或支付。

## 6. Checkpoint 与回滚

每个实质阶段在实施前创建或更新一个新 checkpoint，文件名为
`docs/checkpoints/CP-<UTC日期>-<主题>.md`。记录至少包含：

```text
checkpoint_id
created_at_utc
base_git_commit
scope_and_non_goals
affected_modules_and_module_books
files_dependencies_processes_devices
commands_and_evidence
decisions_and_approvals
risks_and_data_handling
rollback_procedure
next_gate
```

checkpoint 只追加，不覆盖旧记录；失败尝试也要记录。Git 工作树/提交、测试输出、人工
验收和外部供应商材料分别保存并交叉引用。回滚优先恢复到最近一个已验证 checkpoint，
不得用 `reset --hard`、强制推送或删除证据替代回滚流程。

## 7. 决策闸门与连续性

代理应把长任务拆成短的、可验证的阶段，并在每个阶段报告原因、范围、预期和实际结果。
小决策可以在既定边界内执行，但必须写入 checkpoint；以下事项属于重大决策，实施前必须
暂停并请求用户确认：新增依赖或供应商、启动设备/进程、外部网络或账户、改变 REST/WS
协议、扩大权限或数据保留、接入真实 provider、改变人工验收边界。

为保护安全和隐私，记录使用可审计的决策摘要、命令和证据，不记录或输出隐藏思维链。

## 8. 采用状态

本版本仅完成规则落盘，不代表现有所有模块已经满足最低字段。采用后的首个整改门槛是：

1. 建立 `docs/modules/` 索引和逐模块/递归子模块开发书；
2. 统一所有文档和入口使用项目内部隔离工具链，并补齐启动校验与复现记录；
3. 为现有模块登记 test-only 入口与契约；
4. 建立 `system-helper-manifest.v1` 白名单及其负向测试；
5. 为每个后续阶段建立 checkpoint，并把连接前检查纳入验收。

上述工作完成前，现有高层模块文档只能标记为“部分符合”，不能作为递归模块治理已完成
的证据。
